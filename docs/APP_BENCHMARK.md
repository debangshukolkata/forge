# Business-application benchmark: does DebCraft think like the people who will use the application?

Started 2026-10-16 (user's request). Three realistic briefs in the voice of a requester, with no screens, no fields and no scenarios listed: HR (leave and time off), banking (personal-loan origination) and supply chain (purchase to payment).
DebCraft builds each one; the result is scored against the 360-degree rubric below and compared with the reference design written **before** the runs. The gaps become changes to DebCraft's skills and prompts (section 4).
Briefs: `tests/benchmarks/apps/<id>/prompt.md`. Runs: `C:\Work\ForgeRuns\forge-apps\<id>`. Scorer: `scripts/dev/score_app.py` (collects the plan, questions, screens, fields, rules, tests and screenshots).

## 1. The rubric (each line 0-3: 0 absent, 1 token, 2 solid, 3 what a domain expert would build)

| # | Area | What a good answer shows |
|---|---|---|
| 1 | Discovery | asks only questions whose answer changes the design; states assumptions in a file; separates first version from later; names who is NOT served |
| 2 | Process and workflow | explicit states and transitions; who owns the next step; send-back/rework loops; withdrawal/cancel; SLAs and ageing; escalation; delegation |
| 3 | Screens and navigation | one daily path per role; queues not just lists; detail screens with context to decide; empty, loading, error and "nothing to do" states; bulk actions; keyboard speed; mobile for approvers |
| 4 | Data model and fields | the fields the domain needs (not generic); units, currencies, dates; reference data; unique keys and duplicate detection; history of changes; soft delete |
| 5 | Business rules | rules written down as data (limits, tolerances, accrual, policy bands) that an administrator can change; rules explained to the user when they block something |
| 6 | Roles and separation of duties | role matrix; no self-approval; limits by role; maker-checker where money moves; least privilege; what each role cannot see |
| 7 | Audit, compliance, privacy | append-only trail of who/what/when/why; reason codes; personal and account data masked; retention; regulatory hooks of the domain |
| 8 | Exceptions and edge cases | the real-life cases (see the domain lists in section 3); each handled or consciously deferred and said so |
| 9 | Integration and migration | how today's data (Excel, email, other systems) gets in; import with validation and a dry run; export/hand-off to the next system; stubs that are honest |
| 10 | Reporting per persona | operator, manager, auditor, finance each get the numbers they would ask for; exports; drill-down to the record |
| 11 | Quality attributes | concurrency (two people, one record); volume (thousands of rows: paging, search); security basics; backup and restore; accessibility; local formats and languages |
| 12 | Day-two operation | admin setup without code; notifications and reminders; help text in the domain's words; first-run guide; supportability (logs, health) |
| 13 | Honesty and testing | realistic fictional sample data incl. awkward cases; tests of the rules (not just "page loads"); says what is real, demo or missing |
| 14 | Look and feel | designed for daily use by this person; density that fits the work; consistent states and colours; no admin-template look |

A 15th line is not scored but written down for every run: **what a real user would hit in their first week that the application does not handle.**

## 2. How the comparison is done

1. This file's reference designs (section 3) were written first.
2. DebCraft runs headless on the brief with the machine's default model (gpt-5.4). Questions it asks are answered "use your best judgement" so the run is not blocked and the questions themselves can be judged.
3. The scorer extracts: the questions, the task list and assumptions DebCraft wrote, routes/screens, database tables and columns, rule/config data, roles, tests and their results, screenshots of every screen at desktop width, and the README's honesty section.
4. Each line of the rubric is scored with a short reason; the list of reference screens/fields/scenarios is ticked off (found / partly / missing). The result is a table per domain and a list of the pattern of gaps across domains.
5. Only gaps that repeat across domains become changes to DebCraft; a one-off gap is noted. A fourth domain (not in this list) is run afterwards to check that the change generalises and does not just memorise these three.

## 3. Reference designs (written before the runs)

### 3.1 HR: leave and time off (briefing: 250 employees in India and the UK, Excel today, approvals by email)
**Roles:** employee, line manager, HR administrator, delegate, payroll/finance (read), skip-level manager.
**Process:** request -> (auto-checks) -> manager approval -> (HR approval for long or special leave) -> approved -> taken -> closed; branches: send back, reject, withdraw before/after start, modify an approved request, expiry of unapproved requests, escalation after N days, delegation while the manager is away.
**Screens:** employee home (balances by type with "after this request", upcoming, pending, team out today); request form (type, from/to, half-day at start/end, reason, attachment for medical, delegate, live count of working days after weekends and holidays, balance after, warnings: overlap, team coverage, blackout, notice period, maximum consecutive days); my requests with timeline and withdraw; manager queue (who else is out, balance, coverage, approve/reject with reason, bulk); team calendar (month/week, filters, holidays per country); HR: policy editor (leave types per country/grade: entitlement, accrual, carry-over cap and expiry, negative balance, probation, gender-specific types), holiday calendars (incl. optional holidays), employee directory (join/leave date, location, manager, grade, status), manual adjustment with reason, year-end rollover, reports, payroll export (unpaid days per month), audit log, import from Excel with dry run.
**Fields:** employee id, name, location/country, manager, grade, join date, leave date, work pattern (days/week), leave type, start date, end date, start/end half-day flag, computed days, balance before/after, reason (confidential), attachment, status, approver, decision date, decision reason, delegate, created/changed by.
**Scenarios (checklist):** joiner pro-rata; leaver encashment/forfeit; public holiday inside a leave; half-day on a holiday; leave across year end; carry-over cap and expiry; negative balance rule; overlapping requests by the same person; two team members same days; blackout period; retroactive request limit; cancellation after start (partial); approval by delegate; manager is the requester (skip-level); approval timeout/escalation; sick leave extended and converted; compensatory off; part-time pattern; different weekends per country; privacy of reasons; payroll cut-off; concurrent approval and cancellation; audit of balance changes.
**User struggles:** "will my leave be approved before I book the flight", "I do not know my balance after this request", "my manager is on holiday", "the system counted the holiday as a leave day", "I cannot see who else is out".

### 3.2 Banking: personal-loan origination (briefing: retail bank, 6 branches, applications on paper and Excel today)
**Roles:** loan officer (maker), credit analyst, approver (checker with authority limit), operations (disbursement), compliance/KYC officer, branch manager, internal auditor (read-only); customer (not in the application).
**Process:** intake -> KYC/AML -> credit assessment -> pricing and offer -> approval by authority matrix -> documentation -> disbursement; branches: send back, decline with reason code, withdraw, offer expiry, conditions precedent open, deviation approval.
**Screens:** application intake with customer search and duplicate check; applicant and co-applicant, employment, income, obligations, loan purpose; KYC and documents checklist with expiry and verification state; sanctions/PEP screening result (stub, labelled); credit assessment (bureau score stub, debt-to-income, affordability, policy rule results pass/fail/refer, deviations with reason); pricing and offer (rate by risk band, EMI, fees, APR, amortisation schedule); approval queue per authority level with the full case file; documentation and disbursement (sanction letter, conditions, disbursement instruction); pipeline board with ageing and SLA; customer view; reports (approval rate, turnaround, decline reasons, deviations, portfolio mix, officer productivity); admin (products, rate bands, authority matrix, rules, document types, users and roles); immutable audit trail.
**Fields:** customer id, legal name, date of birth, national id (masked), address, contact, employment type, employer, income (gross/net, frequency), existing obligations, amount, tenor, purpose, rate, EMI, fees, APR, risk band, rule results, deviation reason, decision, reason code, approver, authority level, conditions, sanction date, offer expiry, disbursement account (masked), disbursement date, officer, branch, created/changed by.
**Scenarios (checklist):** duplicate applicant; age limits; income mismatch with documents; sanctions or PEP hit; amount above the officer's/approver's authority; self-approval blocked (maker is not checker); send back with comments; applicant withdraws; offer expiry; rate change between offer and disbursal; co-applicant/guarantor; conditions precedent unmet at disbursal; deviation approval; decline reason codes (adverse action notice); EMI rounding and last instalment; prepayment out of scope (said so); regulatory key-facts statement; PII masking by role; retention; concurrency on the same case; reopening a closed case; audit of every status change.
**User struggles:** "which cases are waiting on me today", "why was this case declined", "what is still missing for disbursal", "I cannot approve my own case", "the customer asks where the application stands".

### 3.3 Supply chain: purchase to payment (briefing: distributor, 2 warehouses, 400 items, Excel and email today)
**Roles:** buyer, warehouse receiver, accounts-payable clerk, procurement manager, finance controller; supplier (not in the application, but PO documents go to them).
**Process:** reorder need -> requisition -> approval by value -> purchase order -> sent/acknowledged -> goods receipt (partial, over, under, damaged) -> supplier invoice -> three-way match -> approve for payment or hold -> paid; branches: PO amendment, cancellation of remainder, return to supplier and debit note, invoice duplicate, invoice without receipt, receipt without invoice (accrual).
**Screens:** dashboard (late deliveries, stock-out risk, invoices on hold, spend); items and stock by warehouse (on hand, reserved, on order, reorder point, safety stock, lead time, units of measure and conversions); reorder suggestions that pre-fill a purchase order; supplier master (terms, lead time, approved items and prices, minimum order, rating); requisition and approval; purchase order editor (lines, prices, tax, delivery dates, ship-to, terms, revisions); PO tracking (ETA changes, expedite); goods receipt against a PO (quantities, tolerance, damaged, batch/expiry, location); returns and debit notes; invoice entry and match screen (PO vs receipt vs invoice, variances, tolerances, exception queue); payment due and ageing; stock adjustments, transfers with in-transit, cycle count; reports (on-time-in-full by supplier, spend, price variance, stock ageing, turns, open commitments); admin (tolerances, approval limits, tax, units); audit log.
**Fields:** SKU, description, unit of measure, pack size, warehouse, bin, on hand/reserved/on order, reorder point, safety stock, lead time, supplier, supplier item code, price, currency, tax, MOQ, PO number and revision, line, ordered/received/invoiced quantity, requested and promised dates, receipt number, batch, expiry, condition, invoice number and date, amounts, variance, match status, hold reason, payment terms, due date.
**Scenarios (checklist):** partial delivery and back-order; over- and under-delivery within tolerance; damaged goods and rejection; price change after PO; PO amendment after partial receipt; cancel the remainder; substitute item; unit conversion (case vs each); duplicate supplier invoice; invoice without receipt; receipt without invoice (accrual); return after payment; negative stock prevention; concurrent receipt and transfer; expiry/first-expired-first-out; multi-currency; lead-time variability in reorder; approval by value and by category; supplier blocked; audit of price and quantity changes.
**User struggles:** "what is late and who do I chase", "the supplier invoice does not match and I do not know why", "I received half and the system closed the PO", "which items will run out before the next delivery", "my warehouse count is wrong and I cannot find out why".

### 3.4 Plant maintenance (the fourth, unseen domain: generalisation check, brief `plant_maintenance`; written before it was run)
**Roles:** machine operator (raises requests), maintenance planner, technician, shift supervisor, stores/spares keeper, plant manager, safety officer.
**Process:** request -> triage and priority -> work order -> assignment by skill and shift -> (permit to work / lockout for risky jobs) -> parts reserved -> work done -> checklist and sign-off -> closed with failure cause and downtime; preventive work orders generated from schedules (time- or meter-based); costly repairs need approval; contractor jobs follow the same path.
**Scenarios (checklist, as in the scorer):** asset register and hierarchy; criticality; preventive schedules by time or meter; breakdown / preventive / inspection types; priority and response targets; skills, shifts and assignment; lockout and permits; spare parts stock and reservation; reorder of critical spares; downtime with cause codes; MTBF / MTTR / availability; backlog and overdue PMs; approval for costly repairs; contractors; shift handover; completion checklists; repeat-failure detection; labour and parts cost; warranty and service history; requests by operators; audit trail.
