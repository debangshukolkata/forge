### 0k. Knowledge speed, knowledge by use, several conversations per project (user report 2026-11-12; analysis only, nothing built)
**What the user reported:** (1) reading the knowledge base takes long, perhaps because the whole conversation is loaded when a project opens; (2) some knowledge is used often and some rarely, and the layer should use that; (3) a project can hold only one conversation.

**What the code does today (read 2026-11-12):**
- The knowledge search never looks at the conversation: it matches the words of the query against the topic files. The conversation costs time in two other ways, see the last two points.
- **Every** `knowledge_search`, `knowledge_write` and `code_map` call first brings the index up to date (`project_view` in `tools/code_map_tool.py`): it walks the whole project copy, reads every source file and hashes it, loads `structure.json` and reads `changes.jsonl` twice. Nothing is kept in memory between two calls.
- Every `knowledge_search` and every re-pin parses the YAML header of **all** topic files (`all_topics`), also for `read` of one topic.
- `knowledge_write` does the whole thing twice (once for itself, once to rebuild the pinned block) and parses all topics again, so `/learn` gets slower with every topic it writes.
- Opening a project walks the repository twice (the user's folder, then the copy) before the first screen.
- Measured on the build machine, 364 source files (2.9 MB), 60 topics: update with nothing changed 0.19 s; `structure.json` 1.5 MB; parsing 60 topic headers **0.88 s**; the search itself 0.007 s. So one `knowledge_search` is about 1.1 s here and one `knowledge_write` about 1.5 s, almost all of it work that repeats. On the office laptop (virus scanner on every file read, 500+ files) expect several times more. **Not measured there.**
- Each tool call is also one round trip to the model with the whole context. `search` then `read` are two round trips; in a long conversation each is slower. This may be the larger part of what the user sees; only a run log from the laptop can tell (`KP0`).
- The pinned topic index takes the first 80 topics **by alphabet**, and the search ranks by words only. Nothing records which topic was ever read.
- A project has one event log (`.forge/transcripts/events.jsonl`) for its whole life. On open the server reads and validates every event and the browser gets all of them, copying its list once per event (`ui-react/src/useForge.ts`). `/clear` empties the model's history but the log and the screen keep everything.
