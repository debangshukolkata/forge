# db

Database access: access levels, scratch schema, introspection, DB requests, table checks.

- **Depends on:** config, errors, safety, workspace
- **Invariants:** DB writes only happen in the scratch schema for the current requirement (safety invariant 4), with one exception the user set (D-608): a single INSERT or UPDATE on the development database after the user approved it on a red card; never a delete or a table change there.
- **Tests:** test_db.py, test_live_db.py, test_dev_db_write.py
- **Decisions:** docs/DECISIONS.md (search the module's feature names); layering is enforced by tests/test_module_boundaries.py.

Keep this file in step with the code: the `Depends on` line is checked against the real imports.
- **Running a copy of the application on its own data (D-568):** `copy_rows.py` (`copy_table`: a table's columns, primary key and rows from a database DebCraft may only read into the scratch schema, with COPY from one connection to the other so rows never pass through the model; credential tables refused; a `where` filter checked as one read-only statement; source-only types become text; serial and identity columns keep counting) and `session.py` (`set_app_variables` / `command_environment`: the application's own database setting names mapped to parts of the scratch connection, names stored in `.forge/db_app_env.json`, values only in the command environment). Tests: test_db_copy.py (local Postgres).
- **The tunnel to the development database (D-605):** `tunnel.py` reads `<DebCraft Home>/tunnels.yaml` (typed by the user; the model cannot change it: program, arguments, local port), and `connect()` calls `ensure_tunnel(target)` first: a port that already answers is left alone, otherwise the command is started in the background (no window, no DebCraft secrets in its environment, output in `tunnel_<name>.log`) and stopped when DebCraft ends; failures become a connection error naming the reason, and an expired Google login asks for `gcloud auth login`. Tests: test_db_tunnel.py.
- **An approved change to the development database (D-608, D-609):** `safety/sql_guard.check_dev_write` lets one INSERT or one UPDATE with a WHERE through (no DELETE, TRUNCATE, DROP, ALTER, CREATE, MERGE, ON CONFLICT, RETURNING, second statement, credential table or system catalog). `dev_write.py`: `plan_write` runs the statement in a transaction that is rolled back and returns the rows after and, for an UPDATE, before (as text; at most 500 rows; an UPDATE needs a primary key and may not change it); `apply_write` runs it again and commits only if the rows are still as planned; `record_write` keeps the old and new values of the changed columns in the project's `.forge/dev_writes.jsonl`; `undo_write` sets an UPDATE back unless someone changed the rows since. An INSERT is never taken out again (that would be a delete). The approval itself is the tool's job (`tools/dev_db.py`, `ToolContext.confirm_danger`).
- **The copied application on the development database (D-610):** `dev_proxy.py` (`DevProxy`, a relay on 127.0.0.1 between the application and the server: refuses statements with DELETE, TRUNCATE or DROP with a database error, remembers writing statements and the server's row counts in `Activity`, whose `summary(only_new)` is the report; passes everything else untouched) and `session.py` (`dev_proxy`, `dev_variables`, `dev_app_values`: the application's setting names get the development user, password and database with the relay's address; `command_environment` then sets no search path; nothing of this is written to disk). Tests: test_dev_proxy.py.
- **Held-back settings (D-613):** `dev_guard.py` (`dev_settings` finds, by value, the settings in the copy's env files that hold the development database's address; `Refuser` answers connections with an error that names the two tools) and `session.py` (`dev_held`, `dev_refuser`, `held_back_values`, `still_held_back`; `command_environment` puts the refusing address under those names until `use_scratch_database` or `use_dev_database` replaces them). Tests: test_dev_guard.py.
